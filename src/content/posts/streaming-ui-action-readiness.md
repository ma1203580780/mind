**流式界面的“可见”和“可执行”是两个不同事件，而它们之间隔着整段生成时间。** 一份 2026 年的受控实验给出了一个直接相关的证据：**把同样时长的停顿放在回答开头或结尾，用户评分比放在中间更差。** 位置比时长更能解释不满——这说明用户评的不是“等了多久”，而是“我看到的画面此刻算不算数”。

<!-- a2ui:Chapter -->
## 01 / 反直觉 / 位置比时长更能解释不满

<!-- a2ui:Prose -->
### 这份实验测了什么

先看这份实验，因为它恰好拆开了我们关心的那件事。**QoNext**（[arXiv:2509.21889v3](https://arxiv.org/abs/2509.21889v3)，v3 日期 2026-09-04）是一篇把网络与多媒体的 QoE（体验质量）方法搬到大模型服务上的论文。它没有停留在“回答对不对”，而是把交互过程拆成可控参数，再用真人评分检验。

论文的做法是：把回答质量（信息密度、内容准确度）和服务质量（输出速度、延迟位置、延迟时长）分别做成自变量。其中延迟位置被切成四档：0（开场）、0.25（前段）、0.5（中段）、0.75（末段）；延迟时长固定讨论 3 秒、5 秒、7 秒三档；输出速度用 0.01、0.05、0.1 秒每 token 三档。参与者需要为每一个受控组合打 1–5 分。

规模是可以核对的：**70 多名中英文母语者，292 个实验场次，15768 条人工评分**。经过剔除异常评分者之后，**保留 15174 条有效评分，汇总成 1020 个 MOS 条目**——所谓 MOS，就是每个条件被多人打了分之后的平均意见分。

<!-- a2ui:EvidenceTable -->
### QoNext 里和“能不能动手”有关的三组数字

| 维度 | 论文设定的档位 | 论文报告的结果 |
| --- | --- | --- |
| 输出速度 | 0.01 / 0.05 / 0.1 秒每 token | 0.05 那一档“引入最大的用户反馈波动”；0.1 那一档“触发 MOS 急剧下降” |
| 延迟位置 | 0（开场）/ 0.25 / 0.5 / 0.75（末段） | 出现在 0.25 或 0.75 的停顿，比出现在中段 0.5 造成的损害“略大” |
| 延迟时长 | 3 / 5 / 7 秒 | 3 秒“对多数用户仍可容忍”，5 秒与 7 秒“带来满意度的明确下降” |

注意最后两行要一起读：**位置造成的差异是“略大”，时长造成的差异是“明确下降”。** 论文自己给出的强弱排序也是这个意思——延迟位置带来的是“温和但有意义的”时间敏感性，其总体影响弱于速度和时长。

但这恰恰是它值得写进产品决策的原因。时长是你能用工程手段压下去的量，位置却是你在不改总延迟的前提下就能挪动的量。而论文在这里给出了一个和直觉相反的结论：**停顿在开头或结尾，比停顿在中间更伤。**

<!-- a2ui:Chapter -->
## 02 / 机制 / 流式输出是数据结构的渐进披露

要理解上面的结果为什么和流式界面直接相关，得先看清流式到底在流什么。

<!-- a2ui:Prose -->
模型吐出的是一段文本，但界面要渲染的通常是**一个结构**：一个 JSON 对象、一棵组件树、一张带字段的表单。这两件事的完成时间不一样。文本是线性的、可以任意截断；结构是有语法的、必须闭合。

一份正在传输的 JSON 在绝大多数中间时刻是**不合法**的。`{"items":[{"name":"` 这种前缀没法解析出对象，解析器只能等你补齐括号和引号。流的每一次到达只保证“比上一次多了几个字符”，不保证“多出了一个字段”。

于是渲染器只有两条路：

**第一条，等到结构闭合再整体渲染。** 用户在前 N 秒看到的是一段灰色的骨架。代价是等待，收益是画面出现的瞬间数据就是完整的。

**第二条，按已到达的片段先渲染。** 画面出现得早，但这一刻的界面是**一个快照**——它描述的是“数据到此刻为止的样子”，不是“数据的样子”。

问题就在这里：**用户看到的是一张完整的界面，他能感知到只有一种状态——“已经出现了”；而系统里其实有两种状态——“解析完成的字段”和“还没来的字段”。** 这两者的落差，就是流式界面所有麻烦的来源。

论文里那三档速度和四档位置，量的正是这个落差在时间轴上的分布。0.01 秒每 token 时，落差小到没人注意，评分高且集中；0.1 秒每 token 时，落差持续存在，MOS 急剧下降。而同样 3 秒的顿挫，放在开场会撞上首因效应——论文明确把开场延迟的放大归因于此；放在末段会撞上峰终效应——论文同样把末段延迟的判断归因于此。中间那一段反而是最安全的，因为它是用户已经在阅读、正在处理内容的时候。

所以第一章那个反直觉的排序其实不奇怪：**开场停顿伤的是“它到底有没有在响应我”，末段停顿伤的是“它到底有没有做完”。** 这两个问题都指向状态的可信度，而中段停顿只延长了阅读时间。用户对“画面此刻算不算数”的敏感度，高于对“还要等多久”的敏感度。

## 03 / 后果 / 按钮比它的参数更早可用

如果第二章的判断成立，那么“控件渲染出来就启用”这个默认做法就有一个具体的坏处。

<!-- a2ui:Prose -->
设想一个旅行清单界面，模型正在流式生成条目。到第 2 秒，界面上出现了前三项，并且按要求把“保存全部”按钮一起渲染了出来。第 4 秒，模型又补上了后三项。

现在有两个版本的用户。第一个在第 2 秒点了保存——他保下来的是一个 3 项的快照，界面当时也确实显示 3 项，他没有看错任何东西。第二个等到第 5 秒再点，拿到 6 项。

**界面没有骗人，但它把“当前快照”和“最终结果”混成了同一个可点击对象。** 用户要自己承担判断“现在是不是可以动手了”的责任，而界面没有给他任何判断依据——因为渲染出来的 3 项和前 3 项长得一模一样。

这就是“可见 ≠ 可执行”的准确含义。它不是一个关于谨慎的主张，而是一个关于**参数完整性**的事实：

- **读操作**任何时候都可执行。它不改状态，最坏结果是一次基于旧快照的查询，刷新即可。
- **写操作**的可执行性由它的参数决定。参数依赖的那部分数据一旦还没解析完，按钮就是不可执行的，不管它长得多像可以点。
- **不可逆的写操作**（付款、发布、删除）还要多一层，因为一次错误执行的代价不能被后续的重新渲染撤销。

所以判据不该是“这个控件出现了吗”，而该是**“这个控件需要的字段，是不是都已经解析完了”**。渲染进度和参数完整度是两条独立的线，它们的交错点必须显式对齐，而不是靠“反正一起画出来”来默认对齐。

<!-- a2ui:DecisionTree -->
### 按控件的参数来源决定何时启用

| 控件 | 它的参数从哪来 | 什么时候启用 |
| --- | --- | --- |
| 纯展示文本、标题、预览列表 | 不产生动作 | 一到达就渲染，不必等 |
| 跳转、展开、复制 | 只需已渲染的那部分 | 到达即可用；不改状态，错了可以重来 |
| 提交、保存、下单 | 依赖完整集合或某个字段全解析完 | 等依赖字段全部解析完成，再启用 |
| 付款、发布、删除 | 依赖 + 不可逆 | 等依赖全部解析完成，并且在界面上明示生效范围是哪个快照 |

第三、四行是这篇文章要落到的唯一一条工程规则：**按钮的启用条件，是它的依赖满足，不是它的元素出现。**

## 04 / 中断 / 半张界面看起来像用户填错了

流式界面还有一处位置风险，和末段延迟同源：连接断在半路的时候。

<!-- a2ui:Prose -->
用户看到的是一张填了一半的界面。问题在于，**“生成未完成”和“用户输入错误”在屏幕上长得一样**——都会表现为某些字段是空的。如果界面不做区分，用户会以为是自己没填完，于是去补它，而补出来的是他自己的内容，不是模型的内容。

这解释了为什么第三章那条判据在中断场景下更值钱。定好了“每个控件声明自己的依赖”，中断时就能逐个判断：依赖已满足的控件保持可用（已生成的内容不会丢），依赖未满足的控件保持禁用并给出原因（“仍在生成，还有 3 项”）。两种状态在视觉上必须可区分，否则用户无法知道该等还是该填。

论文里那个 7 秒的数字在这里提供了一个粗略的量级感：**当停顿达到 7 秒这个档位时，多数人的反应已经是明确的负面情绪与脱离**，而不是“再等一会儿”。用户在这种状态下做的补救动作，质量不会高。

至于重连后重复到达的片段：它属于**参数完整度之外的第二层问题**——同一个字段被写了两次。这要求接收端把到达的片段当作**对同一个对象的更新**来处理，而不是当作新对象追加。否则界面会一边补内容一边往下堆，用户看到的是两份互相矛盾的清单，而他此刻正要按第三章那条规则去点保存。

论文在这一点上没有给出数据，我也不打算替它给。

<!-- a2ui:Takeaway -->
## 那个 1 秒

回到开头。同一段 3 秒的等待，放在开场或末段就比放在中段更让用户不满——QoNext 用 15174 条有效评分量出了这个差异的方向。它测的是聊天，不是流式表单，但机制是同一个：**用户评判的不是等待的长度，而是他在等待期间看到的东西此刻算不算数。**

流式界面的价值是让等待有反馈。它不该顺带把“系统准备好了没有”这个判断转交给用户。**渲染完成和参数完整是两条线，按钮只在第二条线上有资格启用。** 前半句是这篇实验支持的，后半句是我从它推出来的工程结论，没有独立的原型实验。
