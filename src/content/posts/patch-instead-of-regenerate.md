一篇稿子大部分已经满意，只想把开头写自然一点。改完开头是好看了，后面的例子换了、校对过的数字也变了。于是我们得出一个很自然的结论：**能不能只改我指的那一处，别动其它地方。**

这个结论有一份实测报告。2026 年 9 月的一项研究训练了四个代码编辑模型——两个从零开始的小模型和两个微调过的 Qwen2.5-Coder-0.5B，架构、训练数据、评测脚本全部相同，唯一变量是输出方式：一种是**整文件重写**，一种是**逐步补丁**（模型输出一串 search/replace，机械应用到当前文件上）。同一批约 1790 道 Flutter/Dart 编辑任务上，静态分析通过率是 **80.2% 对 34.7%**，另一个架构是 **90.0% 对 50.1%**。补丁式输出了少得多的 token，代价是 45.5 和 39.9 个百分点。

更值得看的不是这个差距有多大，而是它从哪里来。

## 缺口不在"补丁打错了"，在补丁打对了地方

补丁式失败最容易被想象成机械故障：搜索串在文件里找不到，或者格式坏掉，工具根本应用不上。实测否掉了这个解释。81%–85% 的补丁轨迹是**正常结束**的——模型明确发出了停止信号，每一步 edit 都成功应用到了文件上。而全部失败里，约 **84%**（Rainbow-Pony）和 **70%**（Qwen）发生在这种"正常结束"的轨迹里。

失败被定位到一个更隐蔽的动作上：**定位**。当模型给出的搜索串在文件里出现多次时，系统不能直接拒绝——那样任何一句短而通用的文本都会变成必然失败——于是用了一个启发式：替换**第一处**出现的位置。

| 轨迹类型 | Rainbow-Pony 通过率 | Qwen 通过率 |
| --- | --- | --- |
| 全程没有歧义匹配 | 57.0%（795 条） | 80.0%（919 条） |
| 至少用过一次歧义回退 | 12.3%（730 条） | 17.5%（537 条） |

通过率差近 5 倍。论文自己的判断是：**这些歧义目标不是数据的问题，是模型自己造出来的**——它发出的搜索串本身就匹配多个位置，而回退规则无法可靠区分。哪怕最后两边代码都能编译，这种"改错了同名的另一处"依然会残留：作者把两侧都通过的样本单独送给盲评模型打分，整文件重写在目标达成（3.89 对 3.44）、正确性（4.14 对 3.71）、代码质量（4.46 对 3.96）上全部更高。

这就是"只改一处"的第一个反直觉之处：**patch 的操作被局部化了，patch 的定位没有被局部化。** 你要改的那一句，在文本里可能不是唯一的；而"是不是唯一的"这件事，在写下修改指令的那一刻是看不见的。

## 补丁的代价随链条长度增长，而收益不涨

如果定位是唯一的问题，那把补丁限制在一两步内就能解决。论文恰好做了这组配对分析，结论比想象的更硬。

作者按轨迹长度切分胜率：在 1–6 步内，补丁式的盲评胜率还有 **10%–18%**；到 14–19 步，降到**接近 0%**。这条下滑曲线在所有六个"任务类别 × 架构"的切分里方向一致。反过来看原始分数就更清楚：随着轨迹变长，补丁式自己的得分稳定下降，而整文件重写在同一批行上的得分基本持平。胜率的崩塌不是独立现象，就是这两条线的剪刀差。

论文把它归到一个变量上，叫 **task locality**：这次修改在空间上有多窄、多自足。它给出的证据不是类别标签，而是每类的平均编辑步数——补丁式唯一赢过整文件重写的两个类别（重构、错误处理与边界情况），恰好是九个类别里平均步数最低的两个。

| 类别 | Rainbow-Pony 平均步数 | Qwen 平均步数 |
| --- | --- | --- |
| 重构类编辑 | 4.14 | 4.49 |
| 错误处理与边界情况 | 6.84 | 7.24 |

论文的机制解释值得抄下来：**整文件重写付的是一笔固定成本**（不管你实际改了多少，都重新生成一遍）；**补丁付的是随轨迹长度增长的成本**。每多一步，就多一次"歧义回退挑错同名位置"的机会，多一层误差沿依赖链累积，多一段模型不再整份重读的文件状态需要它自己记住。论文的原话是：对超过寥寥数步的修改，这个成本的增长快于它省下的 token 收益。

于是"局部修改只重生成受影响部分"这句话的真正含义变了。它不是在为"少算一点"背书，而是在说：**唯一被允许变小的东西是 token 数，不是判断量。** 每砍掉一次整篇重读，你都要用某种别的方式补回对全局状态的掌握；补不回来，代价就会以"安静的错改"的形式记账。

## 改一处，后面整段失效：这不是实现粗糙，是坐标系决定

上面还是文本层面的问题。再把镜头推到模型内部，同一个矛盾会以更硬的形态出现——而且这次有精确数字。

2026 年 8 月的一篇系统论文（PatchKV）研究的就是"只改中间一段"这个动作。它的前提描述几乎就是我们改稿子的场景：长期运行的 agent 会修订上下文里的一小段，同时保留后面很长的内容不变。论文指出一件事：

> "Although the retained suffix preserves its token IDs, each suffix token now observes a different causal prefix and may occupy a different rotary position. Its cached state can therefore diverge from the state produced by an exact prefill of the revised context."

后面那段文字的 token 一个都没变，但它们观察到的前缀变了，所处的位置编码也变了。所以它们**缓存下来的状态**和"把改后的整段重新算一遍"得到的状态不再相同。两条路各有代价：全部重算，扔掉大量已经做过的工作；全部复用，把过期状态带进生成结果。论文把真正的目标写成了一句可以直接搬给编辑器的判断：

> "The central challenge is thus not to maximize cache hits, but to reconstruct only the states that materially affect generation and restore the remaining states at the lowest possible movement cost."

也就是：难题不是提高局部命中的比例，而是分清哪些被牵连的部分**真的影响结果**、哪些不影响。论文的解法是预测"编辑导致的状态漂移"范围，再加上注意力的排序，只重算这个集合，其余降精度还原。代价对比很实在：相对全量后缀重算加速 **2.51–3.85 倍**，相对 CacheBlend 加速 **1.26–2.06 倍**，九个设置里六个 F1 打平或更高，其余最多低 1.36 分。而作为对照的"直接复用全部后缀 KV"，在 Llama-3.3-70B 三个任务上，光把过期状态修回来就值 **51.5–85.1 个 F1 分**。

这说明"局部修改"在带依赖的缓存里几乎从来不是局部操作。位置一变，后续所有依赖历史的状态都进了一个"与全量重算不等价"的集合，你必须为这个集合单独做一次判断和一次计算。

那么"只重算受影响部分"能省到多少？另一篇 2026 年 9 月的论文给了这个比例的一个实测点。它处理的是适配器版本更新后缓存过期的问题，做法是分层判断：只重算真正需要恢复行为的那部分层。结果是**只重算 5.44% 的层**，把平均 KL 散度相对"直接用过期缓存"降低 **92.4%**，缓存维护时间相对全新全量预填充降低 93.2%。

这两个数字要一起读。**直接复用过期缓存造成的偏差，是重算 5.44% 的层就能修掉 92.4% 的量级**——换句话说，过期状态里绝大部分是纯损失，不是无害的噪声。而另一面：能省下来的也只有那 5.44%，剩下 94% 多的层依然要算。**局部化能省的是"重算的冗余"，不是"重算的必要"。** 把这条搬到写作和编辑上，就是那句容易被跳过的话：改一处之后，真正需要重新建立的不是被改的那一处，而是所有依赖它的那些判断——而依赖关系不是文本的字面重复，是语义上的引用，机械比对找不出来。

## 成熟系统怎么处理这件事：把"重算"当成正确性的成本

这套矛盾不是 AI 编辑独有的，只要系统里存在依赖和缓存，它就会出现。两个成熟系统给出的答案几乎一致：**别指望把范围压小，先把依赖图和它的重算成本算清楚。**

PostgreSQL 的物化视图是最直白的例子。`REFRESH MATERIALIZED VIEW CONCURRENTLY` 就是"增量式"的那条路——刷新时不锁住并发读。官方文档把两边的取舍写得很清楚：

> "Without this option a refresh which affects a lot of rows will tend to use fewer resources and complete more quickly, but could block other connections which are trying to read from the materialized view. This option may be faster in cases where a small number of rows are affected."

代价随之而来。这条路**要求视图上至少有一个只含列名、覆盖全部行的 UNIQUE 索引**，并且明确规定：**即使选了这个选项，同一个物化视图同时也只能跑一个 REFRESH。** 换句话说，让更新"局部不阻塞"的代价，是给数据本身加一个全局唯一性约束，并且接受并发度被压到 1。

Bazel 的取舍更直接。它把增量正确性放在第一位：

> "We assume that the build system needs to be first and foremost correct with respect to incremental builds. For a given source tree, the output of the same build should always be the same, regardless of what the output tree looks like."

要做到这一点，Bazel 必须先知道每一步的**全部**输入，才能判断这一步是否还新鲜。它用 Skyframe 显式维护依赖图，"identify exactly which nodes are affected by a given change"，然后做**恢复输出所需的最小工作量**。注意这句里的顺序：先精确、再最小。而且最小化本身也有代价——一个串行声明依赖的节点可能被重启 N 次，成本是 O(N²)，所以节点需要重新组织、甚至拆开。

最有信息量的是 Bazel 对自身边界的交代。它的文档明确写着，即使依赖图是完整的，Bazel 仍然会**泄漏构建时间这类信息、忽略文件属性变更**，并且在 Fileset 和 C++ 规则上存在**已知的正确性问题**。

一个专门为增量正确性而造、连依赖图都显式建模的系统，依然选择公开自己的正确性缺口。这条正好回收了全文的线索：**"局部更新"从来不是一个关于范围的承诺，而是一笔关于依赖图完备性的负债。** 当你把范围压小，你没有消掉计算，只是把它转移成了"哪些部分是受影响部分"这个判断——而这个判断的准确率，就是上面那些数字的全部来源。

## 结语

回到开头那份稿子。真正让人不敢动它的，不是"整篇重来太贵"，而是重来之后不知道哪些地方变了、为什么变。补丁式编辑许诺解决前者，实测显示它把成本挪到了后者：45.5 个百分点的通过率差距里，大头不是打不上补丁，是打上了、打在了错的位置上，并且没有人报错。

所以可用的判据不是"能不能只改一处"，而是这样两条：

第一，**先量链条长度，再决定用哪种方式。** 平均一两步就结束的修改（改个措辞、修一处边界情况），补丁是划算的；需要连续多步、并且每一步都依赖上一步结果的修改，整篇重写是更省的默认值——省的不是 token，是判断。这个门槛不该由感觉决定，可以用同一批稿子跑三到五轮局部修改，直接统计轨迹步数。

第二，**把"受影响范围"当成需要被验证的输出，而不是输入。** 让工具明确报出两件事：这次直接改了什么，以及哪些位置因为一致性要求被一并牵连。前者是可以核对的，后者才是真正需要人来点头的部分。会报依赖的系统（Bazel 那样）和不会报的系统，差距不在它算得多准，而在它承不承认自己算不准。

## 资料与边界

- [Diffs vs. Whole Files: An Empirical Comparison of Iterative Edit-Based and Direct Generation for Flutter/Dart Code Models，arXiv:2609.05779](https://arxiv.org/abs/2609.05779)（v1，2026-09-05 提交）：约 1790 道 Flutter/Dart 编辑任务的同架构对照；静态分析通过率 80.2% 对 34.7%（Rainbow-Pony-100M）、90.0% 对 50.1%（Qwen2.5-Coder-0.5B），差距 45.5 与 39.9 个百分点；81%–85% 的补丁轨迹正常结束，84%/70% 的失败发生在正常结束的轨迹里；无歧义回退 57.0%/80.0% 对有回退 12.3%/17.5%；盲评三项分数（3.89/3.44、4.14/3.71、4.46/3.96）；轨迹 1–6 步胜率 10%–18%、14–19 步接近 0%；两个类别平均步数 4.14/4.49 与 6.84/7.24。边界：单一 Flutter/Dart 领域、模型规模限于 100M 与 0.5B、两项微调 regime 的 token 预算并不相等（论文在 Limitations 中自行披露），结论不应外推到任意语言或任意规模的模型。**本文正文未使用该论文的 ar5iv 镜像，仅取 arXiv abs 与 html/v1。**
- [PatchKV: Efficient KV Cache Recovery for Dynamically Edited LLM Contexts，arXiv:2609.26219](https://arxiv.org/abs/2609.26219)（v1，2026-08-18 提交）：中间编辑不破坏后缀 token ID，但改变其因果前缀与旋转位置，因此缓存状态与精确重算不等价；目标不是最大化缓存命中，而是只重建真正影响生成的状态；相对全量后缀重算 2.51–3.85 倍加速，相对 CacheBlend 1.26–2.06 倍，九个设置六个 F1 打平或更高、其余最多低 1.36 分；相对直接复用后缀 KV，在 Llama-3.3-70B 三个任务上恢复 51.5–85.1 个 F1 分。边界：三个模型、三个长上下文问答负载的 CPU offload 原型，不是生产服务实测。
- [CacheReforge: Bounded Recovery for Stale KV Caches under Evolving Adapters，arXiv:2609.30884](https://arxiv.org/abs/2609.30884)（v1，2026-09）：适配器持续更新导致缓存过期；只重算 5.44% 的层，平均 KL 散度相对陈旧复用降低 92.4%，缓存维护时间相对全新全量预填充降低 93.2%。边界：Qwen2.5-1.5B 与 7B、LoRA 持续更新场景，非通用编辑场景。
- [Challenges of Writing Rules，Bazel 官方文档](https://bazel.build/rules/challenges)（HEAD 版，核对于 2026-10-05）：增量构建以正确性为首要目标；需知道构建步骤的全部输入；Skyframe 精确识别受变更影响的节点并做最小恢复；串行声明 N 个依赖的节点可能被重启 N 次、成本 O(N²)；文档自述仍会泄漏构建时间信息、忽略文件属性变更，并存在已知正确性问题。
- [REFRESH MATERIALIZED VIEW，PostgreSQL 官方文档](https://www.postgresql.org/docs/current/sql-refreshmaterializedview.html)（current 版，核对于 2026-10-05）：`CONCURRENTLY` 避免锁住并发读；不带该选项时大量行刷新资源更少、完成更快但会阻塞读连接；该选项在小行数场景可能更快；要求至少一个仅含列名且覆盖全部行的 UNIQUE 索引；即使启用，同一物化视图同时只能运行一个 REFRESH。

未采用的来源：有二手页面与聚合站转述过"diff 式编辑更省 token 所以更好"的说法，本文没有引用，因为其数字无法回到一手页面核对；Aider 的编辑格式基准（论文多次引用）为持续更新的第三方榜单，本文只把它当作背景，不作为任何数字的来源。
