DeepSeek 的官方价目表上，同一百万 token 有三个价：命中缓存的输入 **$0.003**，未命中缓存的输入 **$0.15**，输出 **$0.60**（以上都是非高峰价；高峰价整体翻倍成 $0.006 / $0.30 / $1.20）。最贵与最便宜之间是 **200 倍**。这三行数字来自同一台机器、同一份权重、同一次请求——差别只在这段文字是"已经算过"还是"现在要算"。

如果软件产品的边际成本可以写成"多复制一份，成本约等于带宽和存储，四舍五入是零"，那么上面这张表就是反证：AI 产品每多服务一个用户，账上会多出一笔按次计的算力支出。这笔支出里唯一能被"存起来下次直接用"的部分是输入；输出没有缓存这条路，只能用时间换价格。

## 一 / 价目表是边际成本的自白书

厂商比谁都清楚自己的成本结构。看他们把价格切成几段，就等于看他们把钱花在哪一段。

拿同一份官方页面的两行来对齐。**DeepSeek V4 Flash**：命中缓存输入 $0.003、未命中 $0.15、输出 $0.60（每百万 token，非高峰价）——注意输入有两个价，输出只有一个。**DeepSeek V4 Pro**：$0.022 / $0.66 / $1.98。两行各自独立，不变的是比例：缓存命中与未命中之间是 50 倍（Flash）和 30 倍（Pro），输出与缓存命中之间是 200 倍和 90 倍。

再看 **Amazon Bedrock** 上的 Claude 3.5 Sonnet v2：输入 $6.00、输出 $30.00、batch 输入 $3.00、batch 输出 $15.00、cache write $7.50、cache read $0.60。输入比输出便宜 **5 倍**，cache read 比输出便宜 **50 倍**。

把这 6 行数字摊在一起，会看到一条稳定的规律：

| 环节 | 相对价格 | 能不能靠优化压掉 |
| --- | --- | --- |
| 缓存命中的输入 | 最便宜，约 1× | 能，取决于请求前缀重复率 |
| 未命中缓存的输入 | 约 25–64× | 能，改成命中就走上一行 |
| 输出 | 约 90–200× | 只能换算法，不能缓存 |

问题的核心在最后一行。缓存是把"已经算过的注意力结果"存下来复用；输出 token 没有这个选项，因为第 N 个 token 必须等第 N-1 个算完才能开始算。Hugging Face 的缓存策略文档把这件事写得很直白：自回归模型**每次预测一个 token**，每个预测都依赖前面的 token，所以模型"每次都在做同样的计算"——KV 缓存解决的是把这份重复计算存下来，不是消掉它。

这就定义了两种成本性质完全不同：

- **输入是存储问题。** 同一段说明、同一份系统提示词、同一批文档，第二次出现时几乎免费。它的成本会随前缀重复率下降，甚至能压到名义价格的百分之一。
- **输出是计算问题。** 用户要多少新内容，就要跑多少次前向计算。它按次发生，与用户总数无关，也无法被缓存。

所以「多服务一个用户」在 AI 产品里不是复制字节，是**再跑一遍推理**。前者是存储与带宽，边际成本趋近于零；后者是计算，边际成本是一个正数，且由这一次的输出长度决定。

## 二 / 这笔钱花在哪：从 GPU 小时到 token

价目表说的是"卖多少钱"，还没有说"花了多少钱"。DeepSeek 在开源周的最后一篇工程说明里，罕见地把成本侧也报了数：**2025 年 2 月 27 日 12:00 到 2 月 28 日 12:00（UTC+8）** 的 24 小时里，V3 与 R1 推理服务的峰值节点占用 278 个，平均占用 226.75 个（每节点 8 张 H800）；按每张 H800 每小时 $2 的租赁成本计，**当日总成本 $87,072**。同一时段内，输入 token 共 **608B**，其中 **342B（56.3%）命中磁盘 KV 缓存**；输出 token 共 **168B**；平均每输出一个 token，KV 缓存长度约 **4,989 token**。

这几行数字能解释上一节那张表为什么长成那样。

**第一，缓存命中率是一个可以被观测的运营指标。** 56.3% 不是一个理想值，是一次真实流量的实测值。这个比例决定了输入类成本落在 $0.003 那一行还是 $0.15 那一行，而它取决于产品里有多少请求共享同一段前缀——比如同一份系统提示词、同一份知识库、同一段对话历史。

**第二，KV 缓存长度解释了"输入为什么不是免费的"。** 平均每个输出 token 背后挂着近 5,000 token 的缓存长度。缓存省掉的是**重算**，不是**读取**：这段上下文每生成一个 token 都要参与一次注意力计算。上下文越长，每个输出 token 要读的缓存越多。长上下文不是加一点成本，是抬高整条输出曲线的斜率。

**第三，成本的分母是时间，分子是顺序。** 平均输出速度 20–22 token/秒，这个数字讲的是延迟；反向看，它意味着一张 GPU 每秒能产出的输出 token 有一个上限。批处理可以把多路请求塞进同一张卡，把吞吐拉高，代价是每路的延迟变差——这两条曲线只能交换，不能同时改善。

有了成本侧的锚点，就能算清"规模"到底能省多少。按当天实际口径，$87,072 ÷ 776B token ≈ **每百万 token $0.11 的算力成本**；而厂商的对外标价是每百万输出 token $0.60 起。中间这段毛利不是靠用户变多挤出来的，是靠同一张卡上塞进更多并发、把更多输入变成缓存命中挤出来的。

同一篇说明里还有一组更常被引用的数字：如果所有 token 都按 R1 的价格计费，当日理论收入 $562,027，**成本利润率 545%**。但原文紧接着列了三条为什么实际收入远低于此——V3 定价本身显著低于 R1、Web 和 App 免费、非高峰自动折扣。545% 是"满负荷 + 全部计费 + 全部命中缓存"的上界，不是一个可以照抄的经营结果。

这里要把两件事分开：**规模经济**和**网络效应**不是一回事，它们作用在两条不同的曲线上。

| | 规模经济 | 网络效应 |
| --- | --- | --- |
| 作用对象 | 你的单位成本 | 用户获得的价值 |
| 随用户增长 | 成本曲线下移 | 产品对每个用户变好 |
| AI 产品里的载体 | 硬件议价、批处理利用率、缓存命中率 | 基本没有，除非产品本身有共享结构 |
| 可观测指标 | 每百万 token 成本、缓存命中率 | 用户之间的互相增益 |

DeepSeek 的数据支持第一列的三个载体：平均占用 226.75 个节点而峰值 278 个，说明利用率已经被压得很紧；平均 4,989 的 KV 缓存长度和 56.3% 的命中率，说明缓存这条路已经在走。但**没有一个数字支持第二列**——多一个用户不会让另一个用户的写作更好。私人写作工具、单人知识库这类产品，用户增长只买来便宜的算力，买不来产品变好。把它们当成网络效应产品来设计增长策略，是在赌一个不存在的曲线。

## 三 / 用这条曲线看功能取舍

把上面两节的机制落成判断，只需要问一个问题：**这项能力花的钱，落在可缓存的那一段，还是落在必须现场生成的那一段？**

可缓存的那一段，成本会随着重复而坍缩，值得用工程手段去榨——把稳定的系统提示词和知识库固定在请求前缀里、把重复的中间结果落盘、把不要求即时返回的批量任务改成 24 小时窗口跑。Amazon Bedrock 和 Azure 都把这笔账写成了公开的价目：batch 相比按需**降价 50%**，cache read 相比按需输入**降价 75%**（Azure 侧的表述是 Batch API "50% discount on Global Standard Pricing"、"24-hour target turnaround"）。

但要看清这两种折扣的不对称。**能缓存的只有输入**：DeepSeek 的价目把输入切成命中与未命中两行，却只给输出一行价格。batch 是另一种东西，它同时给输入和输出打五折，代价是把返回时间放宽到 24 小时——它没有让活儿消失，只是把活儿挪到你不需要即时结果的时候，再去填满机器的空闲。两个机制合起来才是真实账本：**靠"存"省下来的只落在输入，靠"等"省下来的才碰得到输出。**

必须现场生成的那一段，只能靠产品定义去控制。以下三件事都是从上面的机制直接推出来的，不需要额外假设：

**延迟要求决定成本下限。** 既然吞吐和延迟只能交换，那么"用户能等 24 小时"的任务和"用户要看着字往外蹦"的任务，成本天生差一档。把不需要即时反馈的部分从交互链路里挪出去，是唯一能真正压掉输出成本的动作——它不是优化，是重新定义这次请求。

**上下文长度是一个定价决策，不只是技术决策。** 平均每输出 token 挂着近 5,000 token 缓存长度，意味着把上下文从 5,000 加到 50,000，改变的不只是输入费用，还有每一个输出 token 要读的量。往上下文里塞东西之前，先确认它会在这次生成里被用到。

**缓存命中率要当成一级指标挂在看板上。** 它同时决定成本和延迟，而且它是你能从真实流量里读出来的、最接近"单位成本"的运营数字。DeepSeek 敢把它写进公开说明，是因为它已经是一个被日常盯着的量。

## 回到开头那 400 倍

同一个模型，同一段文字，命中缓存和现场生成之间差 400 倍。这个差距不是定价技巧，它照出的是成本结构本身：AI 产品的边际成本由两部分组成，一部分是可缓存、会随重复坍缩的输入，一部分是按次发生、无法复制的输出。

软件分发之所以便宜，是因为第二次复制不需要再做任何工作。推理之所以不便宜，是因为第二个用户要的那段文字，机器必须真的算一遍。用户从一千涨到一百万，能让第一部分的单价往下走，能让算力采购更划算，但**不会让第二部分的性质改变**——它始终是每服务一次就发生一次的成本。

所以「多服务一个用户，成本就接近零吗」的答案不是"接近零但略高"，而是：它是一条有斜率的曲线，斜率由你产品的输出量决定，你能优化的是斜率的截距，不是斜率本身。
